### 处置卡快照与复核导出

每张推出去的卡都落一份**不可变快照**：三个渠道的渲染原文 + 要素数据 +
配置版本 + 阈值表版本 + 制度版本。事后复核读快照，**不重新渲染** ——
阈值表改版、制度改版、配置热载入之后重新渲染出来的内容，已经不是当时推给
值班人的那一份了。

```bash
bash scripts/demo.sh                                                   # 产卡并落快照
python3 -m critval.cli export --event demo-event-0001 --format text    # 取回当时的纯文本卡
```

三个阶段分别是：**只算不落库**（把纯计算开销与落库开销分开，否则说不清「慢是慢在
判定还是慢在写库」）、**端到端落台账**（空库插入）、**幂等重放**（同一批帧再跑一遍，
台账事件数不增加 —— 重复帧被幂等键 `MSH-10 + OBX-3 + OBX-14` 挡住，既有事实不被覆盖）。

单帧耗时含**解析、规范化、判定、落库与出卡**全部环节 —— 只测解析会漏掉 SQLite 写事务，
而值班人等的就是这整段。峰值内存双测：`tracemalloc` 堆峰值按阶段重置（分阶段），
`resource` 进程 RSS 是进程级高水位（只增不减）。

**断点续跑**：回灌中途被打断（进程被杀、机器重启）后从游标继续，不必从头再来。
游标按「来源文件 sha256 + 已处理帧数」记录 —— **文件内容变了游标就作废、从头重放**
（宁可多放一遍，也不能拿旧偏移去读新内容）。单帧失败记入失败清单并推进游标，
不无限重试；读不懂的帧进 `unparsed` 审计，一条都不丢。

```
  加速比          7.321×
  结论            增量重建快于全量重建 ✔
```

**两个数字必须同时成立**才有意义：增量重建**只处理内容变了的那一份材料**（判据是
文件 sha256，不是文件名 —— 文件名不变内容改了也算变更），且耗时**低于**全量重建。
没变的那 9 份材料不重新解析、不重新分词、不动倒排表。

索引底座不接模型：中文双字切分 + 词法打分（BM25，参数可配）与项目码精确匹配两路
并行，命中哪一条、为什么排第一都能按公式复算 —— 这也是「同一份材料两次跑出来排序
必须一样」的底气（得分相同按条目 id 升序，不随运行漂移）。

### 值班台的状态色口径（设计 token）

值班台上每条事件的状态徽标都带**中文文字 + 语义色** —— 颜色只由业务状态机决定，不随页面作者的心情变。夜班一眼要能分清「人在等我」和「已经完了」。

| 业务状态 | 值班台上的说法 | 语义色 | 什么时候出现 |
|----------|----------------|--------|--------------|
| `notified` / `pending_ack` | 已推送 / 已推送待回执 | **危急红** `#D93025` | 处置卡已推到值班人，**在等人点确认** —— 不点就要出事 |
| `acknowledged` / `transferred_to_human` | 已确认 / 转人工 | **待确认琥珀** `#E8890C` | 人已经接了手，等回写登记系统或等下一位人接手 |
| `registered` / `archived` | 已回写 / 已归档 | **已完成绿** `#1E8E3E` | 回执已回写登记系统，**事实已生效**，不用再盯 |
| `received` / `judged` / `card_built` | 已接收 / 已判定 / 已出卡 | **信息蓝** `#1F5EFF` | 机器还在跑，不用人管 |
| `failed` / `writeback_failed` | 处理失败 / 回写失败 | **失败深灰** `#5F6368` | 坏了但不是危急 —— 红色留给临床，失败进死信等人处理 |

### 值班台的三态与写操作反馈（真实渲染）

三态各有**独立模板**（`critval/console/templates/states/` 下的 `loading.html` / `empty.html` / `error.html`），互斥、互不串味；四类写操作反馈各走各的语义色。

| 界面态 | 什么时候出现 | 页面给出什么 |
|--------|--------------|--------------|
| **加载** | 首屏 `?bootstrap=1`，或点「刷新台账」时 | 骨架屏 + 一句「在取什么」+ 无脚本时的退路入口 |
| **空** | 整张台账一条都没有 | 为什么空 + 下一步 + **逐条排查**（LIS 推没推 / MLLP 监听在不在跑 / 阈值表版本绑没绑） |
| **错误** | 事件不存在 / 快照缺失 / 阈值表没绑上 / 回写通道没接入 | **错误码**（能抄进工单）+ 怎么办（可执行动作）+ 重试入口 |

四类写操作反馈的语义色（**失败深灰与危急红刻意分开** —— 通道坏了不是病人要死了）：

| 反馈类型 | 语义色 | 文案要点 |
|----------|--------|----------|
| `ack_ok` 确认成功 | 已完成绿 | 回执按 `message_control_id` 幂等回写登记系统 |
| `notify_failed` 推送失败 | 失败深灰 | 处置卡没推到值班群，已进死信队列，本条留在台账里等人处理 |
| `writeback_failed` 回写失败 | 失败深灰 | 回执没写回登记系统，本条保留为待回写，**已确认的回执不丢** |
| `transferred` 转人工 | 待确认琥珀 | 已转人工，原因已进审计流水，本条不再由值班台自动推进 |

要看的地方：

- **跳步被拒那行** —— `card_built → acknowledged` 意味着「没人确认就当已处置」，
  状态机直接拒掉，事件状态原样不动。
- **「去重通知 1 条 / 真实尝试 2 次」** —— 重推是同一次通知的后续尝试，
  「今天推送了多少条」按去重事件数算，不会因为重推被灌大；首次推送时刻
  （`notified_at`）也不被重推覆盖，另用 `last_notified_at` 记最近一次。
- **审计流水九行** —— 每次状态迁移一行，另有确认与回写两条业务留痕；
  审计表是 **append-only**（库级触发器拒改拒删），且只落标本号 / 项目码 /
  时间 / 科室 / 角色 —— 写进患者姓名会**被拒写**，不是脱敏。
- **四问** —— 依据、通知对象、时限、确认人全部取自已落库的事实；
  答不上来的字段会列进「没记录」，不会拿空值糊弄。

### 显式补写失败回执（`python -m critval.cli writeback-retry` 的真实输出）

回写失败有两种完全不同的病因，处置方式也相反：**契约错**（载荷不合登记系统口径）
重试一万次也是一样的错，得人工改数据；**对端暂时不可用**（5xx / 超时）可以重试，
而且必须重试 —— 危急值不等。命令把两者的分类、可否重试、下一步该谁做什么**摊开写**。

```text
$ python -m critval.cli writeback-retry --list
待写队列（1 条回写失败，等补写）：
  · evt-cli-0001 · 718-7 · ICU · 对端服务错误（5xx） · 已试 1 次 · 可重试 是 · 下一步 人工显式补写
       · 末次错误：登记系统返回 500
```

对端还没恢复时显式补写 —— **仍失败就留在待写队列里并继续告警**，退出码 1：

```text
$ python -m critval.cli writeback-retry --event evt-cli-0001 --actor 检验科组长
显式补写 1 条回执：
  · [失败] evt-cli-0001 · 分类 对端服务错误（5xx） · 可重试 是
       · 下一步 留在待写队列 · 继续告警
       · 补写失败：登记系统返回 500（对端服务错误（5xx），可重试）；已确认回执保留，等补写

！1 条仍失败：已保留在待写队列里并继续告警，未被丢弃（下一轮 writeback-retry --all 可再试）
   · evt-cli-0001：留在待写队列 · 继续告警
```

对端恢复后再补一次 —— 成功，状态推进到「已回写」（已生效事实），退出码 0：

```text
$ python -m critval.cli writeback-retry --event evt-cli-0001 --actor 检验科组长
显式补写 1 条回执：
  · [成功] evt-cli-0001 · 台账状态 registered

$ python -m critval.cli writeback-retry --list
待写队列是空的：没有回写失败的事件
```

> **补写前两道闸门**（都在**发出之前**）：
>
> 1. **契约闸门** —— 回写体九字段的必填 / 类型 / 枚举 / 长度上限 / 时刻格式，
>    不过就**一个字节都不发**（不拿对端当校验器），并给字段级原因：
>    `threshold_row：阈值依据行 缺失或为空（必填，≤512 字）`；
> 2. **冲突闸门** —— 同一 `message_control_id` 下内容与既有事实不同
>    （本地已写进过 / 上次是对端不可用此后内容变了 / 远端探针读到不同）
>    → **既有事实一个字都不改**，事件转「转人工」等裁决。
>
> **失败分类直接决定重试策略**：4xx 契约错**不重试**（人工修数据），
> 5xx / 超时 / 不可达**退避重试**（`--max-attempts` 控制次数，默认 1 次即不自动重试）。

## 更多场景（科室与信息科的其余活儿）

以下场景的完整步骤与可复制命令。README 里只留 7 个最常用的。

### 场景 8：质控专员要改召回策略，先拿数据说话

1. 手上有的是一条条的主观感受（"有时候查阈值要翻好几下"），改策略之前先要一把
   尺子。生成标注评测集：每条查询该命中哪条依据，是**生成器真值**定的，不是人挑的。
2. 跑一次评测，拿到三个数：命中率（该找到的找到没有）、Top-N 命中率（排在前几名
   没有）、出处覆盖率（召回的条目有没有带得出手的出处）。附赠分类指标 —— 哪一类
   查询拖后腿一眼可见。
3. 换一组参数再跑一次，两个数字摆在一起对比；改完再跑一次，确认是真变好了。
   材料改版导致指纹对不上时，报告会自己说"本轮数字仅供参考"，不拿旧数糊弄。

```bash
# 1) 生成标注评测集（重跑得到逐字节相同的文件）
python3 scripts/build_eval_set.py

# 2) 跑评测：三个指标 + 分类指标 + 未命中清单
python -m critval.cli eval-run

# 3) 换参数面再跑一次，对比
python -m critval.cli eval-run --structured-weight 0.8 --lexical-weight 0.2 \
  --out reports/eval_report_w82.md --json-out reports/eval_report_w82.json
```

### 场景 9：信息科要给召回参数定值，先扫一遍网格

1. 召回参数（相似度阈值、两路权重）要写进上线配置，不能拍脑袋。跑一次网格
   扫描：在同一份标注评测集上遍历「阈值 × 结构化路权重」，每个网格点给出
   命中率 / Top-N 命中率 / 出处覆盖率三个数。
2. 看对比表：每个网格点一行，**合格 / 排除**与排除原因写在表里 —— 指标最高
   的那个点如果把硬闸门关掉了（阈值 = 0）或把某一路的权重压成 0，它照样列在
   表里，但不得被推荐。
3. 按固定规则挑推荐参数（先出处覆盖率 100%，再最大化 Top-N 命中率，平手时
   看闸门截断量与结构化权重），结论落 `docs/examples/recall_tuning.md`，
   复核时重跑同一条命令即可复算。

```bash
# 1) 扫网格（默认 99 个网格点：9 档阈值 × 11 档结构化路权重）
python3 scripts/tune_recall.py

# 2) 只想快速看一眼：缩网格、只取前 40 条查询
python3 scripts/tune_recall.py --thresholds 0,0.05,0.2 --structured-weights 0,0.5,0.9,1.0 \
  --limit 40 --out-csv /tmp/grid.csv --out-md /tmp/grid.md
```

### 场景 10：信息科要回答「这套召回到底值不值得上」

1. 信息科拿到的是一句质疑：「你们这套混合召回，比直接用关键词搜强在哪？」
   拿一句辩解交不了差，要一张**同口径**的对比表。
2. 跑一次基线对比：纯 BM25 单路（不做结构化精确匹配、不做规则重排、不做
   综合分硬闸门）与融合引擎，在**同一份材料、同一份标注评测集、同样的检索
   深度与 Top-N** 上各跑一遍，三项指标由**同一个评测器**算 —— 差在哪儿只有
   召回做法这一处。
3. 看对比表的两块：三项指标（命中项数 / Top-N 命中率 / 出处覆盖率）与**分类
   指标**（差在哪一族查询上）。结论落 `docs/examples/recall_baseline_compare.md`
   与 `reports/recall_baseline_compare.csv`，复核时重跑同一条命令即可复算
   （两个产物都不写时间戳 → 两次运行逐字节相同）。

```bash
# 1) 跑对比（先要有语料与评测集：scripts/fetch_data.py → scripts/build_eval_set.py）
python3 scripts/compare_baseline.py

# 2) 运维 CLI 同口径（同 critval.compare 的编排代码）
python -m critval.cli recall-baseline

# 3) 只看机器读的两行数据
cat reports/recall_baseline_compare.csv
```

### 场景 11：值班人发现「制度里写着两个上报时限」

1. 夜班收到一条血红蛋白危急值，处置卡上「上报时限」写的是 **10 分钟内**，
   出处指向制度第 19 行。值班人却有印象：制度里好像还有一处写的是 15 分钟。
   —— 处置卡只取**一条**依据，取到哪条由召回排序决定，取错了没人拦。
2. 跑一次差异归因：两路召回给出的依据按「项目码 + 口径字段」对齐比较，列出
   **所有**说法 —— 上报时限有 10 / 15 / 30 分钟三种，各自带文件名、行号与
   章节（哪一章讲的是哪件事，值班人一眼能分）。系统**不替人选一个**。
3. 处置卡的「待人工裁决」区块把各方说法与出处一并摆出，相关要素从「依据齐备」
   降为「待裁决」，并写一条审计（`recall_conflict_detected`，含两方行号）。
   值班人看完再点确认 —— 确认前这张卡不算「已解决」。

```bash
# 2) 一条命令看完整链路：归因 → 处置卡待裁决区块 → 审计落台账
python3 scripts/conflict_demo.py --db /tmp/critval-conflict.db

# 3) 只看机器读的两行数据
python -m critval.cli recall-conflict \
  --threshold "samples/threshold/示例危急值阈值表.xlsx" \
  --policy "samples/policy/示例危急值报告制度.docx" --json
```

### 场景 12：检验科组长要回答「按 LIS 异常标志判和按咱们阈值表判差多少」

1. 科里的老规矩是「LIS 标了异常就报危急值」。这条规矩在**异常但没到危急值**
   的结果上会误报，在**危急但 LIS 没标异常**的结果上会漏报 —— 两头都出事，
   但一直没人量化过差多少。
2. 跑判定基线对比：同一批由院内阈值表生成的样例、同一份阈值表、同一把尺子，
   两种口径各判一遍。表里给出**误报 / 漏报 / 口径分歧检出数 / 依据可追溯数**
   四个数，差异按场景拆开（哪几行是告警疲劳、哪几行是漏报）。
3. 结论落到行动：按阈值表判，样例集上误报 0 条、漏报 0 条，每条结论都能翻回
   阈值表的文件与行号；LIS 的异常标志降级为**交叉校验信号** —— 两边对不上时
   留一条分歧记录给科里对齐口径，而不是反过来。

```bash
# 判定基线对比（人读对比表 + 机器读两行数据）
python3 scripts/compare_judge_baseline.py
python -m critval.cli judge-baseline --json
```

1. 医务科来问：昨天夜班那条血红蛋白危急值，**按哪一行阈值判的、通知了
   哪个科室的谁、要求几分钟内回执、最后是谁确认的**。值班人手里只有一台
   值班机，翻 Excel 要十几分钟，还说不准有没有人确认。
2. 按事件 ID 查台账：一条命令把四问答完 —— **依据**（示例危急值阈值表
   .xlsx · 第 2 行 · 示例 v1.0）、**通知了谁**（ICU / 检验科值班技师）、
   **几分钟内**（10）、**谁确认的**（检验科值班技师 · 2026-01-02 08:41），
   另附该事件的推送次数明细（第 1 次首次推送、第 2 次到期重推）。
3. 如果这条**还没人确认**，系统会明说「尚未确认」而不是给个空值；台账里
   也能看到它停在「已推送待回执」，到期复查已经重推过几次。
4. 顺带看统计：今天推送了多少条、其中多少是到期重推（去重事件数与真实

### 场景 17：机器半夜重启，早上的台账还接得上吗

1. 夜班值班机在凌晨被断电重启，守护进程跟着死了。早上开机第一件事**不是**
   手工补录，而是先体检：库完不完整、并发加固在不在、有多少条卡在「已出卡
   未推送」没人管。
2. 守护进程启动时自动按**台账里已落库的事实**续跑：卡已装好没推出去的就补推；
   推送过但状态没来得及更新的，**只补状态不再推一遍**；值班人已经确认过的，
   确认人和确认时刻原样带着走，回写只补一次。
3. 人已经接手的（转人工）、事实已定格的（已回写 / 已归档 / 不危急）**一律
   不自动推进** —— 续跑不替人做决定。
4. 要确认「到底接上了没有」，看续跑结论里逐条的动作：补推成功、只补状态、
   回写失败、推不动（缺通道），每条都写明原因并留审计痕迹。

```bash
# 开机先体检：库完整性 / 并发加固 / 状态分布 / 待办计数（退出码给运维脚本用）

# 守护进程启动时自动跑一轮续跑（按台账状态接着做）
python -m critval.daemon --db data/critval.db

# 模拟一次崩溃重启，看看续跑行为（真 os._exit 硬退出，退出码 9）
```

### 场景 18：信息科要证明「审计流水没被人动过」

1. 医务科或内审要看这一轮的危急值处置流水，问一句「这些记录改过没有」。
   库里那条「只追加不改不删」的触发器挡得住应用代码，**挡不住拿到库文件的
   人**（先摘触发器再改一条，触发器一点忙都帮不上）。
2. 信息科跑一条自检命令：系统逐条重算链式哈希 —— 每条审计行的内容哈希，
   加上上一条的链哈希。内容被改过、链哈希被改过、中间少了一条，三类改动
   都报得出来，并指出**第一个断链在哪一条**（流水号 + 坏在哪一种 +
   期望值 / 实际值）。
3. 结论拿得出手：链完好 → 退出码 0，附链头哈希；发现断链 → 退出码 1，指明
   从哪一条开始对不上。流水可以**连哈希一起导出**成 CSV，交给院外复核方
   重算 —— 不然导出一趟就把「可验证」丢在路上了。

```bash
# 全链校验：正常库 exit 0，断链库 exit 1 并报首个断链位置
python -m critval.cli audit-verify --db data/critval.db

# 机器可读结论（供信息科巡检脚本判合格与否）
python -m critval.cli audit-verify --db data/critval.db --json

# 连链哈希一起导出，拿到院外也能重算校验
python -m critval.cli audit-verify --db data/critval.db \
  --export reports/audit_chain.csv
```

### 场景 19：信息科要回答「这条危急值到底卡在哪一步、为什么」

1. 早上交班时有人问：「昨晚那条血红蛋白怎么没有回写登记系统？」—— 光看
   台账只看到一条 `转人工` 的事件，看不出**卡在哪一步**、**为什么卡**。
2. 处置链把主路径画成了一张图（收到 → 判定 → 召回 → 出卡 → 推送 → 人工确认
   → 回写 → 归档），跑的时候逐步记：每个节点跑没跑、结论是什么。链上任何一个
   环节处理不了，**倒着沿走过的路径找到兜底出口**，把异常交出去，同时事件
   状态落 `转人工` 并写审计 —— 机器处理不了的事交给人，**不静默吞掉**。
3. 结论拿得出手：跑一遍就能看到「跑到第几步停的、失败在哪个节点、为什么」；
   链上配置写错导致同一节点反复绕圈（回路）时**直接抛错**，不会悄悄绕到
   值班人发现「这条怎么一直在转」。

```bash
# 正常路径：八节点全链跑完，台账状态 archived，登记系统收到一次真实 POST
python3 scripts/flow_demo.py

# 注入节点异常：看它怎么回落转人工（登记系统零次 POST，事件留在台账里）
python3 scripts/flow_demo.py --break card_built
```

### 场景 20：交班时有人问「昨晚那条到底卡在哪一步、为什么」

1. 交班会上被问：「昨晚那条血红蛋白怎么没回写登记系统？」—— 台账上只看到
   一条 `转人工` 的事件，看不出**卡在哪一步**、**为什么卡**、**重跑有没有意义**。
2. 处置链跑的时候**逐节点留下一条轨迹**：第几步、哪个环节、这一环花了多久、
   读到了什么、交出了什么、结论是什么；链停在哪儿、后面几环为什么没跑，
   都写在轨迹里。轨迹**随事件落库**，事后一条命令回放即可。
3. 回放给得出答案：停在哪一步（第几步、哪个节点）、为什么停（报错原文）、
   这一环能不能重跑（按节点契约声明：推送与回写是幂等的 → 可以重跑；
   判定是纯计算 → 重跑还是同一个答案，重试没意义）、兜底出口用没用上。
   后面没跑到的环节标「跳过」并注明是在第几步停下的 —— 不留空白让人猜。

```bash
# 跑一遍处置链（轨迹随事件落库）
python3 scripts/flow_demo.py --db /tmp/trace.db

# 回放：停在哪一步、为什么、这一环能不能重跑
python -m critval.cli trace --event evt-flow-0001 --db /tmp/trace.db

# 机器可读版（值班台接这条接口时用同一份数据）
python -m critval.cli trace --event evt-flow-0001 --db /tmp/trace.db --json
```

### 场景 22：信息科确认「值班机上那个进程还活着吗」

值班机没人盯着，最怕的是**静默故障**：进程还在、端口还通，但事件不处理了。
信息科不靠「任务管理器里有没有这个进程」判断，而是看**心跳文件**与**健康检查**。

```bash
# ① 心跳文件：外部脚本随时可读（原子写，读到的一定是完整一份）
cat data/heartbeat.json

# ② 健康检查：状态 + 队列深度 + 处理计数 + 三个出站依赖通不通
curl -s http://127.0.0.1:8760/healthz | python3 -m json.tool

# ③ 顺手确认没有第二个实例在偷偷推卡（第二个实例会自己报错退出，退出码 3）
python3 -m critval.daemon --db data/critval.db ; echo "退出码 $?"
```

预期：心跳文件里的 `updated_at` 一直在往前走；`/healthz` 返回 `status=ok`
（出站依赖配了却连不上时是 `degraded`，并写清哪个依赖不通）；
第二个实例打印「另一个守护进程已经占着这个数据目录」并以**退出码 3** 退出 ——
不静默并存（两个实例会把同一张处置卡推两遍）。
