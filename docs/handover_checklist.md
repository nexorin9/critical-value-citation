## 一、五项必查（逐项确认）

### ① 守护进程活着吗

**怎么看**

```bash
# ① 心跳文件：每个心跳周期原子写一次，看修改时间距今多久
#    Linux: stat -c '%y' data/heartbeat.json     macOS: stat -f '%Sm' data/heartbeat.json

# ② HTTP 健康检查
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8760/healthz

# ③ 开机体检（顺带看台账状态分布与待办计数）
python3 -m critval.cli doctor
```

**合格标准**

| 检查 | 标准 |
|------|------|
| 心跳文件 | 修改时间距今 **不超过 3 倍**心跳周期（默认 90 秒内） |
| `/healthz` | 返回 `200` |
| `doctor` | 退出码 `0`（没有 `error` 级异常项） |

**不合格怎么办** —— 心跳不更新或 `/healthz` 不通：

```bash
systemctl status critval                # 看是不是进程挂了
sudo systemctl restart critval          # 重启
# 重启后未处理完的事件会按幂等键续跑，不会丢
```

重启后**必须重跑一遍这五项**再接班。

---

### ② 生效的材料版本对吗

阈值表和报告制度都可能刚换过版。**判错版本 = 按错的阈值判危急值**，
所以每班都要确认当前生效的是哪一版。

**怎么看**

```bash
# ① 当前生效的规则集摘要（规则条数 / 生效版本 / 缺口条数 / 规则快照 ID）
python3 -m critval.cli rules-summary --threshold <本院阈值表路径>

# ② 版本共存与生效期检查（当前生效版本 / 版本空档 / 口径冲突）
python3 -m critval.cli version-check --threshold <本院阈值表路径>

# ③ 材料投递目录有没有新文件（指纹变了会自动重装）
python3 -m critval.cli kb-watch --dir data/materials
```

**合格标准**

| 检查 | 标准 |
|------|------|
| `rules-summary` | 「缺口条数」为 **0**（有缺口 = 有项目码没绑上阈值，那些结果判不了） |
| `version-check` | 没有「版本空档」；口径冲突已由检验科组长裁决 |
| `kb-watch` | 报出来的新增 / 变更事件**都已处理**（确认过才 `--apply`） |

**不合格怎么办**

- 有缺口条数 → 拿 `probe --item <项目码>` 试判，看是没绑版本还是表里真没这个项目；
- 有版本空档 → 某段时间没有生效版本（观察时刻落在空档里 → 该条转人工），找检验科补版本；
- 有新材料事件没处理 → 先跑 `kb-watch`（不加 `--apply` 只看事件），
  看 `parse-queue` 里有没有待人工回填的行列，确认后再 `--apply` 重建。

### ③ 当班名单来源对吗

通知对象来自排班系统。**名单取不到或过期 = 处置卡推给了不该推的人**。

**怎么看**

```bash
# ① 排班系统能不能读到（读得到就说明通道通）
python3 -m critval.cli roster-resolve --roster <排班响应文件> --at "2026-01-01 08:00"

# ② 当班名单缓存新鲜度（默认有效期 900 秒 = 15 分钟）
#    缓存过期时系统会标注来源为 cache 且已过期
```

**合格标准**

| 检查 | 标准 |
|------|------|
| 名单来源 | 是 `live`（实时读到），或 `cache` 且**未过期** |
| 通知对象 | 唯一（一个科室一个当班人；有歧义时值班长兜底） |
| 交班时刻 | 交班后名单已刷新（缓存有效期覆盖到本班结束） |

**不合格怎么办**

- 排班系统读不到 → 查 `NURSE_ROSTER_BASE_URL` / `ROSTER_TOKEN` 与网络；
  实在读不到时通知对象会空缺，处置卡会标注「当班人未解析」，**人工打电话**；
- 名单过期 → 等缓存刷新，或临时改 `CRITVAL_LISTEN_BASE_URL` 之外的手工名单兜底；
- 交班后名单没更新 → 让排班系统把本班人员同步过来，再重跑 `roster-resolve`。

### ④ 待补写的回执队列是空的吗

本地台账与院内登记系统对不上时，回执补写队列会积压。**积压 = 登记系统里缺记录**。

**怎么看**

```bash
# ① 只看待写队列（失败分类 / 次数 / 下一步），不补写
python3 -m critval.cli writeback-retry --list

# ② 全量对账，看本地与登记系统的差异清单
python3 -m critval.cli reconcile --db data/critval.db --out reports/reconcile_diff.csv
```

**合格标准**

| 检查 | 标准 |
|------|------|
| 待写队列 | **空**（没有「回写失败待补写」的事件） |
| 对账差异 | 无 `missing_remote`（登记系统缺记录）；`field_mismatch` 已确认是口径差还是真漏 |

**不合格怎么办**

```bash
# 逐条补写（会调登记系统，失败自动重试可重试分类）
python3 -m critval.cli writeback-retry --event <事件ID> --actor "检验科组长"

# 差异清单按建议动作显式处理（必须带 --actor，审计要记人）
python3 -m critval.cli reconcile --resolve --actor "检验科组长"
```

补写仍失败 → 登记系统侧的问题（网络 / 令牌过期 / 字段不匹配），转给信息科，
按 [troubleshooting.md](troubleshooting.md) 第 3 条走。

---

### ⑤ 死信是空的吗

推送重试耗尽的事件落**死信**（事件不丢，等人处理）。死信非空 = **有危急值没人收到**。

**怎么看**

```bash
python3 -m critval.cli notify-queue --db data/critval.db
```

输出里看三行：

| 输出 | 含义 |
|------|------|
| 队列条数 / 待处理 | 已降级到本机队列的处置卡（企微推不出去时的落点） |
| **死信条数** | 重试耗尽、必须人工介入的事件 —— **本班必须清零** |
| 投递尝试记录 / 投递轮次 | 每次推送的尝试与轮次，用来判断是网络问题还是配置问题 |

**合格标准**：**死信条数为 0**；待处理队列里的条目要么已补推、要么已转人工并有记录。

**不合格怎么办**

1. 死信条目逐条看「未推送原因」；
2. 企微 webhook 没配 → 补 `CRITVAL_WECOM_WEBHOOK_URL` 后热载入；
3. 网络不通 → 恢复网络后重新推送（`notify-queue` 会显示投递轮次）；
4. **本班来不及处理的，必须人工电话通知当班人，并在值班台点确认** ——
   系统不会自动补，人工通知的记录照样进台账与审计。

## 三、交接时不能跳过的事

| 情况 | 必须做 |
|------|--------|
| 机器重启过 | 五项全查一遍，并额外跑 `audit-verify`（确认链没断） |
| 材料刚换版 | 第 ② 项要查到**具体版本号**，不能只看「无缺口」 |
| 有人工电话通知的危急值 | 在值班台点确认，让它进台账与审计；口头交接不算 |
| 死信清过 | 在交接单备注里写清「哪几条、什么时候补推的、确认人是谁」 |
| 交班时正有待回执事件 | 写清事件 ID 与已过时限，接班人接手盯回执 |

**原则**：系统给的结论是**待人工确认的建议**。值班人点了确认才算数；
**没确认的事件不会自动变成已生效事实**，也不会被自动判定为完成。

## 四、每班一条命令的快检

时间紧就只跑这一条（等价于第 ①④⑤ 项）：

```bash
python3 -m critval.cli doctor && python3 -m critval.cli writeback-retry --list && python3 -m critval.cli notify-queue
```

三条都跑完、退出码都是 0 且「死信条数 0」「待写队列空」，本班机器侧就正常。
名单与材料版本两项按第 ②③ 项查。
